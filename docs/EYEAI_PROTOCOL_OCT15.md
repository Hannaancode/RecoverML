# EyeAI-inspired study protocol

This protocol rebuilds a study whose earlier claimed local outputs are unavailable. New measurements receive new timestamps and do not replace those missing measurements with invented evidence.

The scientific motivation is the EyeAI example in Li et al. *From Data to Decision: Data-Centric Infrastructure for Reproducible ML in Collaborative eScience* (2025), Sections VII-A and VII-B, https://arxiv.org/html/2506.16051v1. It describes many historical models and an upstream feature extraction issue followed by revised extraction and downstream retraining. Our experiment is inspired by that workflow. It is not a reproduction of EyeAI patient data, glaucoma performance, or its exact feature defect.

Before running the experiment we fix the configuration in `configs/eyeai_rebuild_oct15.json`. We use all 20 STARE fundus photographs and all 20 Adam Hoover vessel annotations from the published research authors' pinned public repository `sraashis/deepdyn` at commit `48018b62a245dd791e45d60b28068489a8c32742`. Every acquired file is checked against its Git blob SHA-1 and recorded with a SHA-256. The acquisition report lists all files and URLs. Inputs are resized to 64 by 64. Fifteen images train the models and five images test them. We sample 6000 field-of-view pixels from training images only. There is no image overlap between training and test.

Three fixed seeds, two estimator families and histories of 2, 8 and 16 versions produce 18 captures. The first half of each history uses a spatially misaligned feature extractor with a three-pixel shift. The second half uses aligned features. This is an actual change in extracted values, deliberately introduced to model a recorded processing revision. Logistic models use a fixed C sequence and forests use 24 trees with maximum depth 8 and fixed version seeds. These are constructed histories on real images rather than independently obtained production histories. Version settings and related seeds are not independent datasets.

The targets are either all historical models and held-out probability predictions or those targets plus the corresponding extracted features for an investigation. Availability is intact code, possible retirement of the legacy extractor, or possible retirement of training and prediction capabilities. The allowed fault sets are respectively one, two and four combinations including intact operation. Retained files remain intact. We do not claim disk-failure tolerance.

Methods are RecoverML's exact optimizer and a forward robustness-aware greedy baseline and a stronger reverse-delete/local-exchange baseline and native DVC target snapshots and native DVC snapshots of all stages. Each method has the same roots, target list, fault contract and common metadata byte accounting. DVC native cache and pointer overhead is reported separately. Snapshot recovery invokes native DVC checkout and verifies the actual target bytes. Availability conditions reuse those receipts rather than calling reused receipts additional native commands. Recovery requests execute from disk with no access to the capture archive and record timestamps, elapsed and process CPU time, process I/O counters, hashes and operation events. Every target must match its original SHA-256. All ties, losses and failures remain in the results.

The declared grid has 540 method rows and 10920 version recovery requests. CSV progress is flushed per completed row and a complete final ledger is written at the end. Raw logs use complete newline-delimited JSON records, so interruption recovery does not require guessing partial compressed data. Source hashes and the fixed protocol are stored before measurements. Full capture inputs and deduplicated retained-store indexes are packaged for replay.

A separate strong native DVC control will construct ordinary DVC stages for the same recorded operators. It will remove cached downstream outputs and the run cache and physically remove the legacy feature entry point in an isolated temporary directory. The retired entry point must be absent both before and after replay. Freezing the retained legacy feature stage allows DVC to replay downstream models. A matching manual frontier demonstrates DVC's capability and must not be presented as a RecoverML-only capability.

Analysis reports minimum retained bytes, exact recovery, planning cost and restoration cost. Savings against all-stage retention and target-only snapshots are separate comparisons. Exact-versus-heuristic gaps answer whether optimization makes a difference on these histories. Large savings alone do not establish that an exact solver is necessary. A price-free break-even ratio relates measured additional CPU seconds to saved GiB-days over declared restore frequencies and retention periods. We do not invent cloud prices or claim that the 20-image workflow establishes production prevalence.
