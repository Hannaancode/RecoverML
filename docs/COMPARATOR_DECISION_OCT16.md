# Which RecoverML advantages are supported?

Updated 16 October 2026. This decision uses the full saved grids, including ties, slower cases and broader-loss controls.
It is an internal assessment, not external peer review or exhaustive novelty certification.

For the preservation use case, require complete exact recovery under the declared loss contract first,
then compare retained physical bytes among feasible stores, then compare recovery/planning cost.
This is an explicit use-case priority, not a fitted weighted score that makes every comparison a win.
A user who values partial coverage, ordinary pipeline iteration or fastest snapshot loading can prefer a different method.

| Comparator | Supported advantage for RecoverML | Boundary that must accompany it |
|---|---|---|
| Strong robust local search | Shared-loss follow-up: 9/36 smaller stores, 27 ties, up to 48.7380% less storage; median paired planning speedup 16.8822x | All 18 combined-table controls tie; old scientific/retinal/Letter minima also tie. Full-grid median storage reduction is zero. |
| Full scenario exact optimizer | Same exact optimum with median paired planning speedup 1.7327x in the shared-loss follow-up | Established integer minimum-cut machinery on a supported graph subclass; the general fallback need not be faster. |
| Simple greedy | Earlier retinal study improves retained bytes in 12/108 cases and ties 96 | Its stronger local-search replacement matches all 108; no universal heuristic gap. |
| Tested HYPPO rank/frequency components | At RecoverML's minimum budget, full recovery in 36/36 shared-loss histories versus 18/36 and 21/36 | Released components in a common executor, not complete native HYPPO lifecycle replication. Their objectives differ. |
| Implemented HELIX rule | At that budget, full recovery in 36/36 versus 15/36 | Documented rule adapter, not a complete native HELIX implementation. |
| Full target snapshots | Letter preprocessing scope saves 3,664,716,552 canonical bytes, or 290,607,161 bytes with gzip, while retaining exact recovery | Snapshot loading was faster; broad training/prediction loss saves zero. Compressed saving is below one GB. |
| Manually optimized native DVC frontier | Final paired CLI study: 2.1856x median speedup when recomputation is required, 9.9067x when targets are retained; faster in 36/36 tested histories | Identical optimal payload storage. Cold local CLI timings of the authored integrations, constructed histories and three runner blocks; not global DVC inferiority. |
| Manual best frontier as a retention decision | Automated choice and a checkable optimum certificate without a hand-chosen frontier | Manual frontier matches every measured optimum. We do not claim a storage win over an optimum. |

The three defensible contribution categories remain: a precise conditional preservation contract,
an auditable exact retention/recovery implementation using established optimization methods,
and reproducible evidence showing its benefits and failure boundaries.
The file-export improvement is part of the systems implementation.
A new general optimization theory, universal dominance and independent human endorsement remain unestablished.

## Planner follow-up on 26 October

The [complete fixed follow-up](../results/research/planner_efficiency_oct26/RESULTS.md) preserves all 230 frozen optima and reports every slower case. Against the previous implementation, 4,096 independent branches improve by a median 7.824x and a wide retained frontier by 1.950x across three seeds; the small frozen groups remain near parity. Revised planning is faster than local search in 212/230 conditions and scenario exact in 217/230, so neither comparison is a universal win. Storage parity with the manual optimum remains unchanged.
