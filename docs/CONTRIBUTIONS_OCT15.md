# RecoverML contributions in plain words

This statement is based on the code and the saved evidence rather than a guarantee of publication. It describes three contribution categories and does not claim three separate new mathematical inventions.

## 1 A precise promise about old ML results

RecoverML records which files came from which processing steps and which recorded files have the same bytes. The researcher declares which processing capabilities might disappear and which old results must remain recoverable. RecoverML then chooses files to keep under that exact promise and charges each retained physical file once together with the recorded metadata.

For example several experiments may use the same old feature extractor. Keeping every model is one safe option. Keeping the shared feature file and replaying the surviving training step can be another. The system checks the declared failure scenarios rather than assuming that every old command will always work.

The candidate application distinction is the combination of exact historical file identity and a byte objective and a bounded loss of correlated processing capabilities. Content addressing and lineage and materialization and recovery are established ideas. The broader contract still needs independent originality review against robust source selection and explanation problems.

## 2 A checked implementation for that promise

The implementation uses established integer optimization and Horn reachability. It provides two different exact formulations and component decomposition and recovery certificates. A result is labelled optimal only when the selected exact procedure has the required proof status and its recovery checks pass. Unsupported outcomes and timeouts remain visible.

The fresh component study has 154 control rows and 110 use the same contract. All of their tested certified byte objectives agree. It also compares the indexed certificate with an independent fixed-point scan on two chain lengths. These checks support implementation correctness within the tested model. They do not make generic hitting-set optimization or worklist indexing new discoveries.

## 3 Evidence about when storage reduction is useful

The evaluation compares storage and complete exact recovery and planner cost and recovery cost where those measurements are available. It includes public-recipe histories and declared processing losses and released-component baselines and simple retention controls. Every experiment must keep its input hashes and protocol and raw evidence and its negative outcomes.

The fresh annotation sweep has 5760 structural conditions and shows that baseline cost and access and eligibility settings affect decisions. The component audit also shows that equal-output alternatives provide no extra retained-payload benefit on its four real-recipe captures and that deduplication contributes only 431 bytes for one capture. This helps distinguish a mechanism demonstrated by a constructed fixture from a frequent practical benefit.

The exact current benchmark counts and application results must be read from their reconciled result reports. A win over snapshot storage does not establish a win over a manually chosen replay plan and a faster recovery does not automatically establish minimum retained bytes. The intended empirical contribution is an honest map of these tradeoffs.

## Present verdict

There is a concrete working research system and a clear formal task and useful validation work. Strong new theoretical originality and universal superiority have not been established. The [novelty review](NOVELTY_REVIEW_OCT15.md) gives the close prior work and the finite-scenario reduction to weighted Horn abduction. A paper can report these three contribution categories if its scope and comparisons remain accurate.
