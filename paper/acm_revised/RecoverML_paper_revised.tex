\begin{abstract}
Machine learning experiments leave many versions of data and models, and an old result may depend on a processing step that is no longer available. RecoverML chooses which files to keep for a defined set of possible losses and checks that recovered files match their original hashes. Its exact planners find and certify the smallest store under the stated physical file model. In a 56-case decision-rule study with the same robust storage limit, RecoverML restores all 3,344 requests while the tested HYPPO rank and frequency components restore 2,240 and 2,291 and the best tested HELIX rule setting restores 1,940. A later five-candidate storage choice uses exact deltas and joint compression and reduces storage against the earlier flat optimum in 244 of 444 measurable conditions, with 200 ties and a largest reduction of 89.84\%. Against local search with the same formats it wins 20 and ties 424, with two Letter conditions unmeasured. The median saving against that control is zero and an equal-format exact reference matches the certified minimum. At the same optimal stored files, RecoverML is faster than the tested native DVC integration in all 864 census configurations while a direct executor is near parity. A final-file-API study recovers 32,256 of 32,256 requests exactly and measures higher throughput with four process replicas in all 12 fixed cases. The results show gains in recovery coverage, storage and command execution for the measured histories.
\end{abstract}

\section{Introduction}

Researchers change data, features and model settings as an ML experiment develops, so one project can leave many related datasets, fitted transformers, models and predictions. HELIX and HYPPO use shared work to reduce repeated execution, and collaborative workload systems also organize these files for later reuse~\cite{helix,hyppo,collab}.

Older versions remain useful when someone needs to inspect an error or recover the output behind a reported result. In EyeAI, Li et al. recorded more than 70 datasets, 130 executions and 142 trained models, and their records helped trace poor diagnosis performance to an earlier optic nerve extraction step~\cite{derivaml}. That case motivates keeping access to old results, though it does not measure the storage saving from our method.

For example, an image pipeline may turn raw images into features and then use those features to train a model and make predictions. If the old feature extractor disappears, keeping only the images will not recover the earlier features. Storing those features may be enough when training and prediction can still run, but if those steps may also disappear then the old models or predictions may need to stay. The choice depends on which historical outputs matter and which processing steps may fail.

DVC records dependencies and can freeze stages so they are not rerun~\cite{dvc}, while Kishu restores earlier notebook states from checkpoints~\cite{kishu}. An old model can also require compatible software to load~\cite{persistence}. RecoverML addresses the file selection question: given a recorded history and a stated set of possible processing losses, which files must stay so every protected output can be recovered exactly?

The recovery contract names the protected targets, mandatory source files and groups of processing steps that may become unavailable together. For every allowed loss, each target must already be stored or be recoverable from stored files and surviving steps. The planner counts each distinct physical file once along with the required metadata, and hashes identify the exact bytes expected at recovery. The guarantee assumes complete recorded dependencies, intact stored files and a supported replay environment.

RecoverML uses exact optimization for the general recorded history and a minimum cut route when the graph passes its eligibility checks. Minimum cut is an established method~\cite{flow}; here a matching integer flow and cut certify the selected store. A separate checker verifies the certificate and the executor checks recovered file hashes. When all requested targets are already stored, direct export returns the verified bytes without loading a model or starting numerical libraries.

We measure storage, planning and recovery separately against strong local search, published decision rules, manually chosen frontiers and native DVC~\cite{artifact}. In 36 histories under shared preprocessing loss, RecoverML uses less storage than local search in nine and ties in 27, reaching a 48.74\% reduction in the largest case. All 18 histories that store an explicit concatenation file tie, and the manual best frontier matches every exact minimum.

In a native DVC comparison, both methods store the same optimal files. RecoverML has a lower median elapsed time in all 36 histories, with median paired DVC to RecoverML ratios of 2.19 for the 18 histories needing recomputation and 9.91 for the 18 whose targets are already stored. Each history has three paired repetitions, and the timing covers command startup and hash checking but excludes setup and planning. Earlier development revisions remain in the artifact and are not mixed into this final comparison.

The later storage study can keep full files, exact prefix and suffix deltas or a jointly compressed archive, and it chooses the smallest complete store from five candidates. It saves bytes against the earlier flat optimum in 244 of 444 measurable conditions and against local search with the same formats in 20, with 424 local ties. Two Letter conditions remain unmeasured. A broader native DVC census compares recovery at the same optimal stored files in 864 configurations and includes a direct executor control~\cite{artifact}.

In a separate study, 28 histories and two loss bounds give 56 cases. At the same robust byte limit and with one recovery executor, RecoverML restores all 3,344 requests per policy while the tested HYPPO components and HELIX rule settings recover fewer. These are comparisons of their adapted file selection rules rather than complete native system deployments~\cite{artifact}.

In the larger Letter experiment, selective retention saves 3.6647 decimal GB of canonical bytes under preprocessing loss, or 290.61 MB with measured gzip. Under broader training and prediction loss it saves no bytes, strong robust heuristics match its storage choice and loading snapshots is faster in the measured recovery run.

\paragraph{Novelty and contributions.}
RecoverML brings together defined recovery requirements, checked file selection and exact recovery of old results. It uses established provenance and optimization methods and makes three systems contributions:

\begin{enumerate}
  \item \textbf{A clear recovery contract.} Protected file identities, mandatory roots and grouped processing losses define what must remain recoverable, while the storage objective counts distinct physical files and required metadata.
  \item \textbf{A checked system.} General exact formulations and a guarded minimum cut route choose files, certificate checks verify the choices and the executor checks recovered hashes. Direct export handles targets that are already stored.
  \item \textbf{Measured choices and costs.} Public data and retinal image histories show how loss grouping and capture boundaries affect storage, and later storage and native DVC studies measure encoding and recovery time with local and manual controls.
\end{enumerate}

\section{Related Work}

\subsection{Materialization and reuse across ML experiments}

HELIX decides which intermediate results to store and whether to load or recompute them in a later iteration, using a flow formulation for reuse and heuristics for storage~\cite{helix}. That work is a direct precedent for RecoverML, which fixes the old outputs that must remain recoverable and finds the smallest store that protects them against the specified processing losses.

Derakhshan et al. organize shared workloads in an Experiment Graph and select files using their size, computation cost and expected reuse~\cite{collab}. Their later work groups shared computation in a DAG and chooses stored results under a byte budget to reduce future execution time~\cite{productionreuse}. RecoverML also uses a shared history, but its decision is based on complete recovery of specified old outputs after stated losses.

HYPPO records alternative producers in a directed hypergraph and uses equivalent results to find cheaper execution plans~\cite{hyppo}, while its later demonstration supports interactive exploration of shared histories~\cite{hyppo2025}. RecoverML adds explicit recovery requirements and checks whether the selected files meet them. Our experiments run pinned HYPPO selection components and a HELIX rule adapter through a shared executor, so they compare these file choices under one byte limit rather than the complete native systems. We also test robust greedy and local search methods designed for our recovery requirement.

\subsection{Scientific provenance and historical state recovery}

Li et al. link datasets, features, executions and assets across scientific workflow versions, and EyeAI uses those records to investigate an earlier feature extraction problem~\cite{derivaml}. RecoverML asks which files from such a history can be omitted while protected old outputs remain recoverable after specified producer losses. Our retinal experiment uses public images inspired by this case; it does not use the private EyeAI clinical workflow.

Kishu records notebook variable dependencies and restores earlier states with incremental checkpoints and checkout operations~\cite{kishu}. RecoverML protects selected immutable files after stated producer losses rather than the full interactive notebook state.

DVC records dependencies and reruns stages, while frozen stages can preserve chosen intermediate outputs without rerunning their producers~\cite{dvc}. A person can choose the same optimal file frontier in DVC, as our native controls confirm. RecoverML automates that choice and checks it against the recovery requirements; the separate latency experiment compares two authored integrations using the same paid stored files.

\subsection{Replay and checkpoint tradeoffs}

CHEX uses execution history and ordered checkpoints to share work across program versions~\cite{chex}. RecoverML instead chooses persistent files so old outputs remain available after specified producers fail. Checkmate uses mixed integer optimization to trade neural training computation for activation memory~\cite{checkmate}; RecoverML uses established optimization methods for a different file recovery objective.

ExoFlow separates execution from recovery and uses task annotations for recovery with exactly-once workflow semantics~\cite{exoflow}. RecoverML checks the bytes of immutable output files in a supported replay environment, and its storage and recovery costs are measured separately because keeping fewer files can make later recovery slower. RecoverML also has a single-host atomic publication path for process crashes; it does not coordinate distributed side effects.

\subsection{Optimization foundations and the remaining distinction}

Implicit hitting set methods already combine a candidate choice with an oracle and learned constraints~\cite{hittingset}. Minimum cost source location studies paid sources under connectivity requirements~\cite{sourceplacement}, and vertex splitting represents vertex costs in a flow network~\cite{flow}. RecoverML builds on these methods rather than claiming them as new algorithms.

RecoverML applies those methods to recorded ML files and checks that its chosen store protects every target under every allowed loss. For eligible DAGs it uses a flow and cut certificate, while the general route handles other supported histories. In the shared loss study, local search misses a smaller store in some cases, and the manual frontier and concatenation controls identify histories with simpler optimal choices.

\subsection{Captured history and physical file identities}

A logical node records an operation, its inputs and parameters, the output hash and size, and whether the operation can run again. The environment record keeps package versions and implementation hashes for supported operators. Arrays and supported models use recorded serialization, so exact recovery means the same bytes rather than a model with similar accuracy.

Several logical nodes may point to one physical file, so the planner charges that file only once. Let $B$ contain the captured physical blobs and let $w_b$ be the nonnegative size of blob $b$. The map $\beta(p)$ gives the physical output of producer $p$, and $D(p)$ lists its physical inputs. More than one producer may supply the same blob, but a producer needs all its inputs. A nonreplayable node remains in the history without providing a recovery path.

Mandatory roots $R\subseteq B$ must stay and the protected targets are $T\subseteq B$, which may include models, probability arrays or older features needed for investigation. Every compared method uses the same manifest and roots. During recovery it cannot read an omitted file from the full capture archive, infer bytes from a hash or replace an old target with a new model.

\subsection{Recovery contract and byte objective}

The capability map places replayable producers in loss groups, and producers that depend on the same entry point may share a group. Ungrouped producers remain available. For the group set $G$ and loss bound $k$, the allowed losses are
\begin{equation}
  \mathcal{F}_k=\{F\subseteq G: |F|\leq k\}.
  \label{eq:faults}
\end{equation}
The requirement covers processing loss while stored files and mandatory roots remain intact. A changed environment or corrupt stored file causes a refusal when safe recovery cannot be proved.

For a retained set $S$, recovery starts with $A_0=S$ and adds the outputs of surviving producers when all their inputs are available:
\begin{equation}
 A_{i+1}=A_i\cup\{\beta(p):p\text{ survives }F,\ D(p)\subseteq A_i\}.
 \label{eq:closure}
\end{equation}
The process stops at the least fixed point $\operatorname{cl}(S,F)$. Starting from stored files stops an unsupported cycle from counting as a recovery path. The complete file selection problem is
\begin{align}
  \min_{S\subseteq B}\quad & m+\sum_{b\in S}w_b \label{eq:objective}\\
  \text{subject to}\quad & R\subseteq S,\nonumber\\
  &T\subseteq\operatorname{cl}(S,F)\quad\forall F\in\mathcal{F}_k,\nonumber
\end{align}
Here $m$ is the size of the fixed manifest and serialized contract. Reported storage includes roots and metadata once. If a separate byte limit is too small, complete recovery is infeasible; maximizing partial recovery then becomes a different objective.

\subsection{General exact formulations}

The scenario formulation uses one set of binary file selection variables across all allowed losses, then records which files and producers are available in each loss case. A producer can run only after its inputs, so rank constraints stop an unsupported cycle from appearing to recover itself. The solver minimizes the file cost in Equation~\ref{eq:objective}, and a grounded recovery check then tests its chosen store. The number of scenarios grows with the groups and loss bound, so the reference implementation refuses grids beyond its stated limit.

The second formulation starts with a storage master that has one selection variable $x_b$ per physical blob. An oracle looks for an allowed loss $F$ and a closed set $C$ that contains the stored files but misses a target. Closed means that every surviving producer whose inputs are in $C$ also has its output there. Such a witness shows that the store fails under $F$, so every valid store must satisfy
\begin{equation}
  \sum_{b\in B\setminus C}x_b\geq 1.
  \label{eq:cut}
\end{equation}
The master adds this constraint and tries another cheapest store. Once the master proves its minimum and the oracle finds no failing loss, the selected store is both feasible and optimal within the recorded model. Timeouts and invalid solutions remain unknown rather than certified. This master and oracle design follows established hitting set and abduction methods~\cite{hittingset}.

Before accepting a solver result, RecoverML checks binary values, the objective, roots and learned constraints. It first tries the DAG route below; otherwise it uses the scenario formulation for at most 64 allowed scenarios and the master and oracle route above that number. This threshold is an engineering choice, so solver status and later checks still decide whether a result is certified.

\subsection{Guarded DAG specialization and its certificate}

The faster route applies only when the physical dependency graph is a DAG after mandatory roots are treated as available and every optional blob has at most one replayable producer. The guard rejects cycles and multiple producers of the same physical output, even when two logical producers wrote identical bytes.

For this subclass, universal recovery when $k\geq1$ is equivalent to recovery with all grouped producers disabled together:
\begin{equation}
 \bigcap_{F\in\mathcal{F}_k}\operatorname{cl}(S,F)
   =\operatorname{cl}(S,G).
 \label{eq:collapse}
\end{equation}
This equality is a way to reason about a fixed store; it does not add a simultaneous loss of all groups to the runtime contract. In topological order, a stored blob is available, an unstored blob with a producer that may fail is not available under every allowed loss, and an ungrouped producer can always supply its output when all inputs are available. Disabling all grouped producers gives the same universal rule. When $k=0$, no producer is disabled.

After this reduction, an unstored blob without a surviving producer is a failure source. Failure can pass through dependencies, and storing a blob stops it there, so protecting targets becomes a weighted vertex cut between failure sources and targets. Each optional blob becomes an input and output vertex joined by an edge of capacity $w_b$, while dependency and terminal edges receive capacity
\begin{equation}
  M=1+\sum_{b\in B\setminus R}w_b.
\end{equation}
Keeping every optional blob costs less than cutting an $M$ edge. This is the standard vertex splitting construction~\cite{flow}; roots and fixed metadata are added to the selected file cost.

NetworkX finds an integer maximum flow and a cut. The checker verifies edge capacities and flow conservation, then removes the chosen stored vertices and checks that no failure source can reach a target. The weight of the stored optional blobs must equal the feasible flow value: the cut gives an upper bound and the flow gives a matching lower bound. A separate grounded recovery check confirms that the store protects the targets.

This reduction does not apply to every AND/OR history. Two producers in different groups may each recover one target after a single group loss, although disabling both would prevent recovery; an unsupported physical cycle also breaks the cut argument. The guard therefore sends these histories to a general exact route.

\subsection{Components and recovery execution}

An optional decomposition removes mandatory roots from the live dependency graph and solves target bearing components separately. RecoverML combines their selected files and pays for global roots and metadata once; solver projections are not saved as capture manifests. Shared loss labels are safe here because each component is checked against every allowed loss relevant to it. There is also a direct rule for one optional target whose producers depend only on roots: the target need not be stored if an ungrouped producer exists or if the number of distinct producer groups exceeds $k$.

For an actual recovery request, the executor finds a grounded path from stored files through surviving producers and follows dependency order. Each request has its own memo and trace, and every loaded or recovered file must match its recorded hash. Missing or corrupt files and source mismatches produce explicit errors. The general restorer checks its supported runtime before loading values and never uses a producer declared unavailable.

When every requested target is already stored, direct export checks its size and SHA-256 identity and writes the output without loading a model. If a target is absent the executor uses ordinary replay, while a corrupt stored target causes an error. Exporting the same bytes does not mean an incompatible environment can run the model.

\subsection{Publication and concurrent recovery}

The durable publisher writes selected blobs, the manifest and contract to a sibling directory, flushes files and POSIX directories, then atomically renames it to the final path on the same filesystem. One publisher owns each destination and readers use only the final path: a process stopped before rename exposes no store, while one stopped after rename leaves a complete store. Published files are read-only; each request owns its restorer, memo, trace and output directory, and success requires exact target hashes. The legacy staging writer remains separate from this guarantee.

\subsection{Histories and declared processing changes}

The shared loss grid uses Wine and Breast Cancer from scikit-learn~\cite{datasets}. A stratified split assigns 75\% to training and 25\% to testing under seeds 20261016, 20261017 and 20261018. Two disjoint feature views are standardized from training data only, and logistic regression versions cover regularization from $10^{-3}$ to $10^3$. One capture boundary lets downstream steps consume both views directly while the other also stores their concatenated matrix.

Each history is tested first with separate preprocessing groups and then with one group covering both standardization steps, always with $k=1$ and the same captured bytes. The shared loss follow-up came after a favorable pilot, so the complete grid retains small histories and explicit concatenation controls. It describes these authored histories rather than the frequency of outages in production.

The scientific matrix adapts Iris feature union, Digits PCA, Diabetes polynomial features and Digits forests. Two seeds and three versions give eight captures, tested under preprocessing and broad loss with $k\in\{0,1,2\}$. Its five budgets pay fixed roots and metadata plus 0, 10, 25, 50 or 100\% of the optional target snapshot bytes, so they are set without using a later optimum. Eight methods produce 1,920 method and budget rows.

The retinal study uses all 20 STARE fundus images and Hoover vessel annotations~\cite{stare}. Images become $64\times64$ RGB, with 15 training images, five test images and 6,000 sampled training pixels. Three seeds, two model families and three history lengths give 18 captures. An aligned extractor replaces a legacy three-pixel feature shift, producing different feature bytes. Targets include models and predictions and sometimes investigation features; the contracts cover intact processing, loss of the old extractor or loss of training and prediction. Model settings also change across versions, and the overlapping histories are not literal nested prefixes despite that wording in the original protocol.

The large study uses all 20,000 UCI Letter observations with 16 features and 26 classes~\cite{letter}. Seed 20261015 gives a stratified split of 15,000 training and 5,000 test observations, while training only MinMax scaling and chi-squared selection keep 12 features. Sixteen trained forests combine 64/128/192/256 trees, two feature sampling settings and two model seeds. The saved files contain no padding or duplicated payload added to reach a storage target.

\subsection{Comparators and budget fairness}

The exact comparators solve the same full recovery problem. Robust greedy adds the largest grounded coverage gain per byte, while our stronger local search also removes unnecessary files from a full store and tries one-file exchanges followed by pruning. It allows at most two exchange passes. Target snapshots store the protected outputs directly, and a manual frontier control selects the smallest feasible frontier using knowledge of each workflow.

The HYPPO rank and frequency methods use a pinned released component and HELIX uses a documented rule adapter. They share the executor and byte accounting, though their selection rules target reuse. In the cloud grid they receive the exact minimum total byte budget while robust heuristics and snapshots can use the full candidate allowance for complete store comparisons. The scientific matrix gives every method the same fixed budget at each point, so the two studies answer different comparison questions.

The separate 56-case matrix gives RecoverML, both HYPPO functions and six HELIX settings the same robust byte limit. HYPPO uses its pinned released component through a physical file adapter. HELIX uses a documented streaming rule reimplementation at 50, 200 and 800 MiB/s with both recorded tie orders. A HELIX control with the larger snapshot budget is reported separately. Every policy uses the same grounded recovery executor, so these results compare file selection decisions~\cite{artifact}.

The native DVC study uses DVC 3.67.1 and gives it the certified optimal retained payloads without charging selection time. One downstream batch stage avoids a separate Python startup for every model, and correctly retained target cache objects can let DVC skip that stage. Before each trial both methods have the same paid physical payloads and no unpaid downstream cache objects, with distinct-inode byte checks and hard links used for common retained files. DVC configuration is recorded separately from the common payload objective. Both authored workers can use the exact file-export helper.

The later encoded storage study retains the previous flat optimum as a candidate, adds exact prefix and suffix deltas with their bases and headers charged, and measures a joint archive of retained canonical payloads. The final selector computes the flat exact, delta exact, flat local, delta local and separately compressed choices and keeps the smallest complete store. We compare it with the previous flat and delta implementation, a joint archive of the flat optimum, and local search with all offered formats. The first three-candidate version lost three conditions to the strengthened local control; adding both local plans was a disclosed correction after that result. Every row in the later table uses the final five-candidate selector, and the original losses remain saved in the artifact~\cite{artifact}. The exact reference only certifies the declared flat or delta inventories, not a global optimum over every jointly compressed retained set.

The later storage catalogue has 216 primary, 48 scientific transfer, 72 three-seed cloud and 108 retinal conditions, plus two Letter conditions whose complete paired storage values are unavailable. These conditions share captures and were chosen for this project, so win fractions describe the catalogue rather than an estimated production probability. All stored byte totals include metadata, mandatory roots and delta bases. Saved file and export checks confirm exact identity but are not new full-grid model replay requests. The joint archive is decoded into memory and uses a temporary retained store for replay; its compression time and peak memory were not benchmarked.

The broader native DVC census has 72 captures from six datasets, four recipes and three history lengths. Three loss contracts, two request sizes and command line or warm API access make 864 configurations, each timed in three paired randomized-order repetitions. The methods receive the same certified optimal retained payloads. The elapsed call includes requested-file inventory and hash verification but excludes capture, planning and setup, and OS caches are not flushed. A separately coded direct executor supplies a control for the cost of DVC orchestration~\cite{artifact}.

\subsection{Machines, repetitions and recorded outcomes}

The shared loss study runs one fixed seed block on each of three Linux GitHub runners exposing four virtual CPUs on AMD EPYC 7763 hosts. The native study uses runners exposing four CPUs with EPYC 9V74 for one block and EPYC 7763 for two. Python is 3.12.15 with NumPy 2.3.5 and SciPy 1.17.0 and scikit-learn 1.8.0, and numerical execution is limited to one BLAS thread. These are separate runner blocks of the same constructed workload design rather than multi node scale-out.

Each cloud planner has three timed calls per case and the earlier 48-condition replanning study has five. General solver calls use a 30 s limit and a requested relative MIP gap of zero, with 120 s allowed in Letter. The polynomial flow route does not enforce a hard interruption deadline. A native recovery comparison has three paired trials with deterministically randomized method order. Its primary elapsed time includes cold subprocess and CLI startup and final common SHA-256 verification, while setup and planning are excluded and worker timings and CPU are logged separately. OS page caches are not flushed. The final native revision follows earlier exploratory corrections and is not pooled with them.

Every actual request records whether its expected target identities were recovered, whether a deficient store was correctly blocked and whether an unexpected outcome occurred. When methods select identical stores they share explicitly attributed execution evidence, so method totals must not be summed as new physical requests. Ratios are computed within a history from method medians and then summarized across histories. These descriptive ratios and repeated requests do not establish population significance.

The final file API runs on a four-vCPU AMD EPYC 9V74 Linux runner. Breast Cancer and Digits have 1, 4 and 16 versions; root-only replay and retained-target export use different measured byte totals. Each condition has three bursts of 128 requests, using 1/2/4/8 threads or 1/2/4 same-host process replicas, for 252 trials. Requests have private outputs; warmup and planning are excluded. Throughput covers submission through completion, service P99 covers execution, and response P99 also includes queue wait. The artifact retains every request, source hash, machine record and independent audit.

\subsection{Broader native DVC recovery census}

In the later census RecoverML exceeds the prespecified 1.10 times elapsed-time threshold against the tested native DVC integration in all 864 configurations. The median paired DVC-to-RecoverML ratio is 1.6952 for the 432 command line configurations and 48.3212 for the 432 warm API configurations. All 7,776 trials restore requested files exactly and the ledger checks 54,540 requested-file hashes. Latest and all-version requests coincide when a history has one version, so these counts do not represent independent workloads~\cite{artifact}.

The direct executor control narrows the interpretation. This census supports a consistent advantage against the specified native path across the authored catalogue, but it does not establish faster model training or a production win probability.

\section{Discussion and Reproducibility}
\label{sec:discussion}

RecoverML first protects complete recovery and then minimizes stored bytes, while recovery time is measured separately. The manual frontier ties and faster snapshot loads show how the preferred choice depends on that objective. The repository provides source hashes, captured file identities, raw timings, solver records and analysis scripts~\cite{artifact}. Its script rebuilds the original figures from recorded inputs, and later storage and recovery ledgers are linked in the same artifact. Fresh runs write to a new output directory, and none of these studies required a GPU.

\section{Limitations}

The datasets are public, but the histories and loss cases were built for these experiments; related seeds, versions and requests do not estimate a production win rate. The favorable shared loss pilot informed a later full grid, and the five-candidate store was corrected after the stronger local control exposed three losses. The retinal study adapts public images rather than the private EyeAI workflow, and Letter's byte saving changes with compression. Annotation effort, deployment cost and how often capabilities disappear remain unmeasured.

Fresh capture and replay passed on three runners, but exact replay across arbitrary software changes was not tested. Six original nonforest scientific captures lack a closed global source guard after an interruption, although their snapshots, request guards and raw reconciliation remain. One original Letter archive container is unavailable; four recovered frontier files match their hashes in a separately identified replacement archive. The joint archive decodes into memory, so its compression time, random access cost and peak memory need measurement. Larger neural states, networked scale out, power-loss recovery and distributed crash consistency remain future work.

\section{Conclusion}

RecoverML records old ML files and chooses a checked store that keeps protected outputs recoverable after specified processing losses. It restores all 3,344 requests per policy in the 56-case decision-rule study at the same robust byte limit, where the tested HYPPO components and HELIX rule settings recover fewer. The five-candidate storage choice improves on the earlier flat optimum in 244 of 444 measurable cases and on equal-format local search in 20, with 424 local ties. The native DVC census also favors RecoverML at the same stored files, while a direct executor is near parity and manual or equal-format exact choices match the relevant storage minima. These results show where the system helps in the measured histories.
