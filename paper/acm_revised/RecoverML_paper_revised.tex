\begin{abstract}
Machine learning experiments produce many versions of data and models and recovering an old result can become difficult when a processing step is no longer available. RecoverML chooses which files to keep for a stated set of possible losses and checks recovered files against their original hashes while its exact planners find and certify the smallest store within the stated physical file model. \reviewone{Against strong local search, median planning was 6.27 times faster on eligible DAGs in the timing study and 16.88 times faster in the separate shared loss cloud study.} In a study of file selection rules across 56 cases under the same robust storage limit, RecoverML restores all 3,344 requests, the tested HYPPO rank and frequency components restore 2,240 and 2,291 and the best tested HELIX rule setting restores 1,940. A later choice among five storage candidates uses exact deltas and joint compression to reduce storage against the earlier flat optimum in 244 of 444 measurable conditions with 200 ties and a largest reduction of 89.84\%. It wins 20 comparisons against local search with the same formats and ties 424 while two Letter conditions remain unmeasured. The median saving against that control is zero and an exact reference using the same formats matches the certified minimum. With the same optimal stored files, RecoverML is faster than the tested native DVC integration in all 864 census configurations and is close in time to a direct executor. \reviewtwo{The final file API recovers all 32,256 requests exactly. Four process replicas raise throughput in all 12 fixed cases.}
\end{abstract}

\keywords{historical machine learning recovery, data provenance, artifact retention, materialization, capability loss, reproducibility}

\maketitle

\section{Introduction}

As researchers change data, features and model settings, one ML project can produce many related datasets, fitted transformers, models and predictions. HELIX and HYPPO reuse shared work to reduce repeated execution and systems for collaborative workloads also organize these files for later use~\cite{helix,hyppo,collab}.

DVC records file dependencies and can freeze stages so they do not run again~\cite{dvc} while Kishu uses checkpoints to restore older notebook states~\cite{kishu} and loading an old model may also require compatible software~\cite{persistence}. RecoverML focuses on finding which files need to be kept from an earlier experiment so that all protected results can still be recovered exactly even when some processing steps are no longer available

The recovery requirements specify which results must be protected and which original source files must remain stored along with the groups of processing steps that may fail together. For every allowed failure the required results must either already be stored or be recovered using the stored files and available processing steps while the planner counts each unique physical file only once along with the required metadata and hashes are used to check that the recovered files contain the same bytes as the originals

RecoverML uses exact optimization to choose which files should be kept and applies the minimum cut method when the recorded graph meets the required conditions. Minimum cut is an existing method~\cite{flow} and RecoverML uses a matching integer flow and cut to prove that the selected files have the minimum storage cost while a separate checker verifies this proof and the executor checks the recovered file hashes. When all requested results are already stored the system can return the verified files directly without loading the models or starting numerical libraries

% Reviewer 1 W1. Separate planning from storage gains.
\reviewone{In the 48-condition study, RecoverML planned faster than strong local search in all 36 eligible DAG cases, with a median speedup of 6.27 times. The separate shared loss cloud study gave a median speedup of 16.88 times.}

We measure storage, planning and recovery separately using strong local search, published decision rules, manually chosen frontiers and native DVC as comparisons~\cite{artifact}. Under shared preprocessing loss, RecoverML uses less storage than local search in nine of 36 histories and ties in 27 with a largest reduction of \reviewone{48.7\%}. All 18 histories with an explicit concatenation file tie and the manual best frontier matches every exact minimum.

A separate study combines 28 histories with two loss bounds to give 56 cases, where every policy receives the same robust byte limit and uses one recovery executor. RecoverML restores all 3,344 requests per policy while the tested HYPPO components and HELIX rule settings recover fewer. HYPPO and HELIX were designed for iterative reuse, so this study tests how their adapted file selection rules meet the stated recovery requirement~\cite{artifact}.

\paragraph{Novelty and contributions.}
RecoverML combines stated recovery requirements with checked file selection and exact recovery of old results. It builds on established provenance and optimization methods through three systems contributions:

\begin{enumerate}
  \item \textbf{A clear recovery contract.} Protected file identities, mandatory roots and grouped processing losses define what must remain recoverable while the storage objective counts distinct physical files and required metadata.
  \item \textbf{A checked system.} General exact formulations and a guarded minimum cut route choose files with certificate checks for those choices and hash checks during recovery. Direct export returns targets that are already stored.
  \item \textbf{Measured choices and costs.} Histories using public data and retinal images show how loss groups and capture boundaries affect storage and later storage and native DVC studies measure encoding and recovery time against local and manual controls.
\end{enumerate}

\section{Related Work}

\subsection{Materialization and reuse across ML experiments}

HELIX decides which intermediate results to keep and whether to load or recompute them in a later iteration, using a flow formulation for reuse and heuristics for storage~\cite{helix}. RecoverML builds on this work by fixing the old outputs that must remain recoverable and finding the smallest store that protects them against specified processing losses.

Derakhshan et al. organize shared workloads in an Experiment Graph and choose files based on their size, computation cost and expected reuse~\cite{collab}. Their later work groups shared computation in a DAG and selects stored results under a byte budget to reduce future execution time~\cite{productionreuse}. RecoverML uses a shared history to choose files that keep specified old outputs completely recoverable after stated losses.

HYPPO records alternative producers in a directed hypergraph and uses equivalent results to find cheaper execution plans~\cite{hyppo} and its later demonstration lets users explore shared histories interactively~\cite{hyppo2025}. RecoverML states the required recovery outcomes and checks whether the selected files meet them. We run pinned HYPPO selection components and a HELIX rule adapter through a shared executor to compare their file choices under one byte limit and also test robust greedy and local search methods designed for this recovery requirement.

\subsection{Scientific provenance and historical state recovery}

Li et al. link datasets, features, executions and assets across scientific workflow versions and EyeAI uses those records to investigate an earlier feature extraction problem~\cite{derivaml}. RecoverML asks which files can be left out of such a history while protected old outputs remain recoverable after specified producer losses. Our retinal experiment applies that recovery question to public images.

Kishu records notebook variable dependencies and uses incremental checkpoints and checkout operations to restore earlier states~\cite{kishu}. RecoverML protects selected immutable files after stated producer losses.

\subsection{Replay and checkpoint tradeoffs}

% Reviewer 1 V2. Related work on dataset recreation and ML intermediates.
\reviewone{Bhattacherjee et al. study which data should be kept so that older versions of a dataset can be created again}~\cite{bhattacherjee2015versioning}. \reviewone{MISTIQUE looks at whether intermediate model results should be loaded from storage or computed again when answering diagnostic queries}~\cite{vartak2018mistique}. \reviewone{RecoverML instead chooses which files need to be kept based on the older results that must be protected and the processing steps that may become unavailable.}

CHEX uses earlier execution records and checkpoints to reuse work across different program versions~\cite{chex} while RecoverML focuses on keeping the files needed to recover older results when some processing steps can no longer run. Checkmate uses mixed integer optimization to decide which activations should be stored or computed again during neural network training to reduce memory use~\cite{checkmate} while RecoverML uses existing optimization methods for a different purpose which is selecting files for recovering older results.

ExoFlow separates normal execution from recovery and uses task information to support exactly-once workflow operations~\cite{exoflow} while RecoverML checks whether recovered files have the same bytes as the originals within a supported software environment. RecoverML also measures storage use and recovery time separately because keeping fewer files may require more processing later and its atomic publication method can handle process crashes on one machine.

\subsection{Optimization foundations and the remaining distinction}

Implicit hitting set methods use possible solutions and an oracle to find missing constraints~\cite{hittingset} while minimum cost source location looks at how to choose sources based on their cost and connection requirements~\cite{sourceplacement}. Vertex splitting is also an existing method for handling vertex costs in flow networks~\cite{flow,ahuja1993flow} and RecoverML uses these methods rather than introducing new optimization algorithms.

RecoverML applies these methods to recorded ML files and checks whether the selected files can recover every protected result under all allowed processing failures. For suitable directed acyclic graphs (DAGs) it uses a flow and cut certificate to verify the solution while other supported histories use general exact optimization and the shared loss experiments show that local search sometimes misses a smaller storage choice although the manually selected frontier and stored concatenation cases also show that some histories have simpler optimal solutions.

\label{sec:method}

\subsection{Captured history and physical file identities}

Each logical node records an operation with its inputs, parameters, output hash and size, along with whether it can run again. The environment record keeps package versions and implementation hashes for supported operators and arrays and supported models use recorded serialization so exact recovery requires the same bytes rather than similar model accuracy.

Several logical nodes may point to the same physical file so RecoverML counts its storage only once. Let $B$ represent the captured physical files and $w_b$ their nonnegative sizes while $\beta(p)$ gives the output file of producer $p$ and $D(p)$ gives the input files it needs. More than one producer may create the same file but each producer needs all its inputs to run while operations that cannot run again remain in the recorded history without providing a recovery path

Mandatory source files $R\subseteq B$ must remain stored while the protected results are $T\subseteq B$ which may include models and probability arrays or older features needed for investigation. Every method uses the same manifest and mandatory files while recovery uses only the selected stored files and available processing steps to recreate the original results

\subsection{Recovery contract and byte objective}

RecoverML places processing operations into groups that may become unavailable together while operations outside these groups are assumed to remain available. Operations that depend on the same entry point or software package or external service should be placed in one group because losing that dependency would affect all of them. The value $k$ defines how many groups may fail at the same time while any producer left outside these groups is assumed to remain available so if this assumption is not safe then its output should be stored or the recovery requirements should be changed. For example if two different producers can create the same optional result using only mandatory source files and each belongs to a different group then losing one group still allows recovery through the other producer but if both groups can fail together then the result must be stored. For the group set $G$ and loss bound $k$, the allowed losses are
\begin{equation}
  \mathcal{F}_k=\{F\subseteq G: |F|\leq k\}.
  \label{eq:faults}
\end{equation}
The requirement covers processing loss while stored files and mandatory roots remain intact and a changed environment or corrupt file causes a refusal when safe recovery cannot be proved.

For a retained set $S$, recovery begins with $A_0=S$ and adds the output of each surviving producer once all its inputs are available:
\begin{equation}
 A_{i+1}=A_i\cup\{\beta(p):p\text{ survives }F,\ D(p)\subseteq A_i\}.
 \label{eq:closure}
\end{equation}
Recovery stops at the least fixed point $\operatorname{cl}(S,F)$ and starting from stored files prevents an unsupported cycle from counting as a recovery path. The complete file selection problem is
\begin{align}
  \min_{S\subseteq B}\quad & m+\sum_{b\in S}w_b \label{eq:objective}\\
  \text{subject to}\quad & R\subseteq S,\nonumber\\
  &T\subseteq\operatorname{cl}(S,F)\quad\forall F\in\mathcal{F}_k,\nonumber
\end{align}
Here $m$ is the size of the fixed manifest and serialized contract and reported storage counts roots and metadata once.

The flat planner certifies minimum paid bytes within its declared file inventory. The delta extension certifies its declared full file and single base delta inventory, including every retained decoding base and metadata cost. The later joint compression selector in Section~\ref{sec:encoded} chooses the smallest actual store among five constructed candidates: the flat and delta optima, and joint compression of the flat optimum and two local search selections. Each choice must meet the recovery contract, while the minimum is over these five candidates rather than all possible jointly compressed retained sets.

\subsection{General exact formulations}

The scenario formulation uses one set of binary file selection variables for all allowed losses and records which files and producers remain available in each case. Rank constraints require a producer's inputs to be available first, preventing an unsupported cycle from appearing to recover itself. The solver minimizes the file cost in Equation~\ref{eq:objective} and a grounded recovery check tests the chosen store.

The second formulation starts with a storage master that has one selection variable $x_b$ for each physical blob. An oracle searches for an allowed loss $F$ and a closed set $C$ that contains the stored files but misses a target, where closed means every surviving producer with inputs in $C$ also has its output there. This witness shows that the store fails under $F$, so every valid store must satisfy
\begin{equation}
  \sum_{b\in B\setminus C}x_b\geq 1.
  \label{eq:cut}
\end{equation}
The master adds the new constraint and searches again for the set of files that uses the least storage and when it proves the minimum and the oracle finds no failure that prevents recovery then the selected files are considered valid and optimal within the recorded model while timeouts or invalid results are marked as unknown. The method follows existing hitting set and abduction approaches~\cite{hittingset}

RecoverML checks the binary values and storage objective along with mandatory source files and added constraints before accepting a solution. It first tries the DAG method and if that cannot be used then it applies the scenario method for up to 64 possible failure cases or the master and oracle method when there are more than 64

\subsection{Guarded DAG specialization and its certificate}

The faster route requires a physical dependency DAG after mandatory roots are treated as available with at most one replayable producer for every optional blob. The guard rejects cycles and multiple producers of one physical output even when two logical producers wrote identical bytes.

For this subclass, universal recovery when $k\geq1$ is equivalent to recovery with all grouped producers disabled together:
\begin{equation}
 \bigcap_{F\in\mathcal{F}_k}\operatorname{cl}(S,F)
   =\operatorname{cl}(S,G).
 \label{eq:collapse}
\end{equation}
The equality describes a fixed store without adding simultaneous loss of all groups to the runtime contract. In topological order, a stored blob is available and an unstored blob whose producer may fail is not available under every allowed loss while an ungrouped producer can supply its output whenever all its inputs are available. For a fixed graph, targets, groups and payload costs, every positive $k$ therefore gives the same feasible retained payload sets and minimum payload cost in this subclass. The case $k=0$ leaves all producers enabled, and general histories with alternative producers can respond differently as the bound increases.

After the reduction, an unstored blob without a surviving producer becomes a failure source. Failure can pass through dependencies until a stored blob stops it, so protecting targets becomes a weighted vertex cut between failure sources and targets. Each optional blob becomes an input vertex and an output vertex joined by an edge of capacity $w_b$ while dependency and terminal edges receive capacity
\begin{equation}
  M=1+\sum_{b\in B\setminus R}w_b.
\end{equation}
Keeping every optional blob costs less than cutting an $M$ edge, as required by the standard vertex splitting construction~\cite{flow,ahuja1993flow}. Roots and fixed metadata are then added to the selected file cost.

NetworkX calculates an integer maximum flow and its matching cut while a separate checker verifies the edge capacities and flow conservation before removing the selected stored vertices and checking whether any failure source can still reach a protected result. The total weight of the stored optional files must match the valid flow value because the cut gives an upper bound and the flow gives a lower bound so when both are equal the solution is proven optimal while another recovery check confirms that all protected results can be recovered

The method does not work for every AND/OR dependency structure because two producers from different groups may each recover the same result when one group fails but losing both groups would prevent recovery while a physical cycle without a valid recovery path can also make the cut method incorrect. RecoverML checks these conditions and uses general exact optimization when the specialized method cannot be applied

\subsection{Components and recovery execution}

RecoverML can divide the dependency graph into smaller parts by removing mandatory source files and solving the parts containing protected results separately before combining their selected files while mandatory sources and global metadata are counted only once. Internal solver results are not saved as experiment manifests and shared failure groups do not cause a problem because each part is checked against every allowed failure that applies to it. For an optional target whose producers only need mandatory source files the target does not need to be stored if an ungrouped producer is available or if its producers belong to more than $k$ different groups

When a recovery request is made the executor finds a valid path using stored files and processing steps that are still available and follows the dependencies in order while each request keeps its own memo and execution record. Every loaded or recovered file must match its recorded hash and missing or damaged files and incorrect source contents produce errors while the system checks the supported software environment before loading values and never uses processing steps that have been declared unavailable

When all requested results are already stored RecoverML checks their file sizes and SHA-256 hashes before returning the files directly without loading a model while a missing target is recovered through normal replay and a damaged stored target causes an error rather than being ignored

\subsection{Publication and concurrent recovery}

RecoverML first writes the selected files and manifest and recovery requirements into a separate directory beside the final location and then flushes the files and POSIX directories before renaming the directory to its final path on the same filesystem. Only one publisher can use each destination and readers access only the final path so stopping the process before the rename does not expose an incomplete store while stopping it afterward leaves a complete store. Published files remain read only and each recovery request uses its own restorer and memo and execution record along with a separate output directory while recovery is considered successful only when the resulting files match their expected hashes

\section{Discussion and Reproducibility}
\label{sec:discussion}

RecoverML first makes sure that all protected results can be recovered and then tries to reduce the storage needed while recovery time is measured separately. The Letter experiment shows this difference because keeping fewer files saves storage but takes longer to recover the results compared with loading stored snapshots so keeping extra checkpoints or outputs may be better when the same results are requested often. Complete recovery is a requirement while minimum storage is the main goal and adding a recovery time limit or considering how often files are requested would be a possible future improvement. The repository keeps source hashes and recorded file identities along with timing results and solver records and analysis scripts~\cite{artifact} while the paper build checks the figures using saved experiment calls and trials and manifests and file records. \reviewtwo{The build creates seven vector figures where six show the experimental results and one shows the system architecture}. New experiments save their results in separate output folders and none of the studies used a GPU

\section{Limitations}

The experiments use public datasets and histories created for this project so the results cannot tell us how often RecoverML would perform better in real systems. Some experiments use the same recorded histories with different seeds and requests while the retinal histories are not exact versions built one after another and requests for the latest version and all versions are the same when a history has only one version. The shared loss experiment was carried out after an earlier pilot gave good results and the final method using five storage choices was updated after stronger local search found three cases where the earlier method used more storage

The recovery method assumes that all dependencies have been recorded and stored files are not damaged and the required software environment is supported. The certificates only prove results for the defined file model while the graph checks cover a limited set of graphs and general exact optimization becomes harder as the number of possible failure cases increases. Six original scientific histories without random forests are missing a completed global source check after an interruption but their saved snapshots and request checks and original records are still available. One original Letter archive is also missing although all four retained files in a documented replacement have hashes that match the originals. The runner experiment checks whether recovered files match the hashes from each runner's own capture but recovering identical bytes across different CPU and BLAS versions has not been tested

The HELIX and HYPPO experiments use adapted file selection methods rather than their complete systems while the native DVC results only cover the implementations used in these experiments. The exact optimization proofs cover the defined flat and delta storage choices but do not prove the best possible result across every combination of jointly compressed files. \reviewtwo{The compression experiment measures the time needed to create and export stored files for two histories but does not include optimization or model replay while the effort needed to record dependencies and deployment costs and how often processing steps become unavailable have not been measured}. The crash tests only cover processes and file publication on one filesystem while larger neural network states and software changes and shared network storage and recovery after power failures or crashes across distributed systems still need further testing

\section{Conclusion}

RecoverML records old ML files and chooses a checked store that keeps protected outputs recoverable after specified processing losses. At the same robust byte limit it restores all 3,344 requests per policy in the study of decision rules across 56 cases, where the tested HYPPO components and HELIX rule settings recover fewer. The choice among five storage candidates reduces bytes against the earlier flat optimum in 244 of 444 measurable cases and against local search using the same formats in 20 with 424 local ties. The native DVC census also favors RecoverML with the same stored files while a direct executor is close in time and manual or exact choices using the same formats match the relevant storage minima.
