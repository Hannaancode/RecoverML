\begin{abstract}
Machine learning experiments leave related versions of data, models and predictions, and recovering an old result may require a processing step that no longer works. RecoverML selects one shared set of files under a declared recovery contract and checks restored bytes against captured hashes. Its exact planners certify the minimum for the stated physical retention model. In a 36-history shared preprocessing study, RecoverML stores less than strong local search in nine cases and ties in 27, while a manual best frontier ties every minimum. We later added exact delta encoding and joint compression. Across 446 related storage conditions, the final five-candidate choice improves on the previous flat optimum in 244 of 444 measurable cases and ties in 200, with a largest reduction of 89.84\%. Against local search with the same offered formats, it wins 20, ties 424 and loses none; two Letter conditions remain unmeasured. The median saving against that local control is zero, and an equal-format exact reference still matches the certified minimum. A separate native DVC recovery census gives both methods the same optimal retained payloads and finds a median paired elapsed-time advantage for RecoverML in all 864 tested configurations. The advantage concerns the measured DVC integration because a direct executor is near parity. These results support a checked historical recovery system with specific storage and orchestration gains rather than a new general optimization or compression algorithm.
\end{abstract}

\keywords{historical machine learning recovery, data provenance, artifact retention, materialization, capability loss, reproducibility}

\section{Introduction}

Machine learning research rarely ends with one execution because researchers change the data and features and model settings as they investigate a question. Each execution can leave processed datasets and fitted preprocessing state and trained models and predictions, and several versions may share much of the same work. Systems such as HELIX and HYPPO already use these shared computations to reduce repeated execution, while collaborative workload optimizers organize artifacts across experiments so that later work can reuse them~\cite{helix,hyppo,collab}.

Earlier versions can also matter after a new model has been chosen because a researcher may need to inspect a processing error or recover the output behind an earlier result. The EyeAI case described by Li et al. provides a concrete example: the project recorded more than 70 datasets and 130 executions and 142 trained models, and its provenance helped trace poor diagnosis performance to an upstream optic nerve extraction step~\cite{derivaml}. The need to inspect that history motivates preservation, although it does not establish how much storage a retention optimizer would save.

Consider an image workflow in which raw images pass through a feature extractor and then a training step produces a model and predictions. If the extractor changes, an earlier feature file may still be needed to explain the old predictions. Keeping only the images and the current extractor cannot reproduce those earlier features when the old extractor is unavailable. Keeping the earlier features can preserve downstream recovery when the recorded training and prediction steps still work, but a contract that also allows those steps to fail may require retaining the models or final outputs themselves. The right files to keep therefore depend on the particular historical outputs being protected and the processing capabilities assumed to survive.

Pipeline tools already support useful parts of this process. DVC records dependencies and outputs and can freeze selected stages so that reproduction does not execute them~\cite{dvc}, and Kishu restores earlier notebook states through incremental checkpoints~\cite{kishu}. Model persistence also has an environment boundary because loading an old model may require compatible software versions~\cite{persistence}. RecoverML addresses a specific decision within this setting: given a captured history and a declared set of possible processing losses, which files should remain stored so that every protected output can still be recovered exactly?

We express this decision as a recovery contract. The contract identifies protected targets and mandatory source files and groups of processing capabilities that may become unavailable together. For every allowed loss, each target must either be retained or have a valid recovery path through retained files and surviving producers. Recorded hashes identify the expected file bytes, and physical payloads with the same identity are charged once together with the required metadata. A set that works for one loss but fails for another allowed loss does not satisfy the contract. The promise assumes complete recorded dependencies and intact retained files and the supported replay environment.

The planner uses exact formulations for the general recorded model and applies a minimum cut specialization when the history satisfies its eligibility conditions. The specialization uses established flow techniques rather than a new graph optimization algorithm~\cite{flow}, and its certificate contains a feasible integer flow and a retained cut with equal cost. A separate checker verifies this evidence and the recovery executor checks the resulting files against their expected hashes. When every requested target is already retained, a direct file export path verifies and returns those bytes without loading a model or starting numerical libraries. File export preserves byte identity and does not imply that an incompatible environment can execute the serialized model.

Our evaluation separates storage selection from recovery execution and keeps strong baselines and manual controls visible~\cite{artifact}. In an exploratory grid using two datasets, 36 captured histories are assessed under both separate and shared preprocessing loss, giving 72 paired history and contract cases. Under shared loss the exact planner improves storage over strong local search in nine cases and ties in 27, with a maximum reduction of 48.74\%. All 18 cases with an explicitly stored shared concatenation file tie local search, which shows that the benefit depends on how intermediate work is captured. The manually chosen best frontier matches every exact minimum.

A separate native DVC experiment gives both systems the same optimal retained payloads and uses one batched downstream DVC stage. With three paired repetitions per history, RecoverML has a lower median elapsed time in all 36 histories and the median DVC to RecoverML elapsed time ratio is 2.19 for the 18 histories needing recomputation and 9.91 for the 18 histories whose targets are all retained. The timing includes subprocess startup and final hash verification and excludes setup and retention planning, so it measures these command line integrations rather than an inherent difference between all deployments of the two systems. Earlier mixed outcomes remain in the artifact as separate development revisions rather than additional trials.

The later storage study changes how retained artifacts are represented. It offers full files, exact prefix and suffix deltas, and joint archive compression, then chooses the smallest complete store from five computed candidates. Across 446 related conditions this choice reduces bytes against the earlier flat optimum in 244 of 444 measurable comparisons, but it improves on local search with the same offered formats in only 20 and ties in 424. A broader native DVC census also measures recovery at equal optimal retained payloads over 864 configurations. We report these complete grids, including the two unmeasured Letter cases and the direct executor control, because the advantages depend on the comparator and objective.

The larger Letter experiment shows another boundary: selective retention saves 3.6647 decimal GB of uncompressed canonical bytes under preprocessing loss, but the saving is 290.61 MB with the measured gzip representation and zero under broader training and prediction loss. Strong robust heuristics match the storage saving and loading snapshots is faster in that descriptive recovery run. These controls help distinguish the value of retaining fewer bytes from the separate questions of optimization difficulty and recovery speed.

\paragraph{Novelty and contributions.}
The contribution of RecoverML is the integration of a declared historical preservation contract with checked retention planning and executable recovery, together with evidence showing how correlated processing loss and capture boundaries change the useful choices. We build on existing provenance and materialization and optimization methods, and the resulting system and measurements make three contributions:

\begin{enumerate}
  \item \textbf{An explicit contract for exact historical recovery.} We connect protected artifact identities and mandatory roots and correlated capability losses to a storage objective that counts physical payloads and required metadata. The contract makes the recovery obligation and its assumptions checkable.
  \item \textbf{A checked retention and recovery system.} We combine general exact formulations with component decomposition and a guarded minimum cut specialization, and provide certificate checks and recovery verified against recorded hashes. A direct export path handles fully retained targets without unnecessary model loading.
  \item \textbf{An empirical account of the useful choices and their limits.} Public data and retinal image workflows measure exact recovery, storage, planning and restoration. Paired local and manual controls expose the effects of failure grouping and capture granularity. Later full-catalogue storage and native DVC recovery studies test exact encoding choices and recovery latency at equal retained payloads, while reporting ties and weaker direct-executor outcomes.
\end{enumerate}

\section{Related Work}

\subsection{Materialization and reuse across ML experiments}

HELIX separates the decision to retain an intermediate result from the decision to load or recompute it in a later iteration, and it uses a flow formulation for reuse planning and heuristics for materialization~\cite{helix}. Its treatment of iteration and intermediate files is a direct precedent for this work. RecoverML instead fixes the historical targets that must remain recoverable and asks for the smallest retained store that satisfies declared processing losses, so a useful reuse plan alone is not sufficient to establish its preservation obligation.

Derakhshan et al. organize collaborative workloads in an Experiment Graph and select artifacts using information such as size and computation cost and reuse frequency~\cite{collab}. Their later production pipeline work groups shared computation in a DAG and chooses materializations under a storage budget to reduce later execution time~\cite{productionreuse}. These studies already establish shared history and storage aware execution planning. RecoverML uses related graph information but evaluates complete recoverability under the stated losses rather than future reuse likelihood or model utility.

HYPPO represents alternative ways to produce artifacts in a directed hypergraph and uses equivalences to find less expensive execution plans~\cite{hyppo}. The later Hyppo demonstration adds interactive discovery and exploration of shared pipeline histories~\cite{hyppo2025}. These systems are close to RecoverML in their use of history and alternative producers, and our distinction is the explicit preservation obligation and its checks. The experiments use pinned HYPPO materialization components and a HELIX rule adapter through a common executor, which supports a comparison of those policies under a declared budget but does not reproduce the complete native systems. We also compare robust greedy and local search policies because a heuristic designed for the same obligation is a stronger decision quality baseline than a policy designed for a different reuse objective.

\subsection{Scientific provenance and historical state recovery}

Li et al. link datasets and features and executions and assets in a versioned scientific workflow, and the EyeAI application shows how these records can support investigation of an earlier feature extraction problem~\cite{derivaml}. That work motivates the need for historical access and provides a broader framework for collaborative provenance. RecoverML studies which captured files can be removed while preserving a specified set of historical outputs under declared producer loss. Our retinal experiment is a separate public image adaptation inspired by this use case and is not an evaluation on the private EyeAI clinical workflow.

Kishu provides time travel for computational notebooks by preserving dependencies between variables and restoring earlier states through incremental checkpoint and checkout operations~\cite{kishu}. Exact historical restoration is therefore already an explicit goal in prior systems. RecoverML protects selected immutable artifact files under a producer loss contract rather than restoring the complete interactive notebook state, and the two systems address different preservation boundaries.

DVC provides dependency tracking and stage reproduction, and frozen stages can preserve chosen intermediate outputs without rerunning their producers~\cite{dvc}. A manually chosen DVC frontier can therefore implement the same retained file choice as RecoverML, which our native controls confirm. RecoverML adds automatic selection and certificate checks around the declared contract, while the separate native latency experiment measures the cost of executing two authored integrations with the same paid payloads. It does not establish that DVC lacks historical recovery or that an optimal DVC frontier needs more storage.

\subsection{Replay and checkpoint tradeoffs}

CHEX uses execution lineage and ordered checkpoints to share computation while replaying multiple program versions~\cite{chex}. Its cache and replay sequence decisions are closely related to the cost of returning to earlier work, although RecoverML selects persistent files to satisfy a recovery obligation after declared producers become unavailable. Checkmate uses mixed integer optimization to trade neural training computation for activation memory~\cite{checkmate}. That result also shows why using an integer optimizer is not itself a new contribution, and its training memory objective differs from preserving historical artifact bytes.

ExoFlow separates execution from recovery and uses task annotations to support recovery choices with exactly-once workflow semantics~\cite{exoflow}. Explicit recovery assumptions and the cost of checkpointing are therefore established systems concerns. RecoverML verifies immutable output identities within a supported replay environment and does not provide distributed exactly-once side effects or general crash consistency. Its storage benefit and its execution cost must be measured separately because retaining an earlier intermediate can save bytes while making later recovery more expensive.

\subsection{Optimization foundations and the remaining distinction}

Implicit hitting set methods already combine a candidate selection problem with an oracle and learned constraints, including applications to propositional abduction~\cite{hittingset}. Minimum cost source location also studies the selection of paid sources under connectivity requirements~\cite{sourceplacement}, and vertex splitting is an established way to express vertex costs in a flow network~\cite{flow}. These are relevant foundations for retention planning and constrain claims of algorithmic originality.

RecoverML applies these foundations to a recorded ML artifact contract and checks that the selected files preserve its protected targets under every allowed loss. Its supported DAG specialization avoids a general integer formulation and provides checkable flow and cut evidence, while the general route handles recorded structures outside that guard. The measured shared loss cases show that strong local search can miss a smaller feasible store, but the manual frontier ties and explicit concatenation controls show that some histories have simple optimal choices. The contribution is a checked preservation service and an account of when its choices matter, rather than a claim that every ML history requires difficult optimization or that the underlying graph methods are new.

\label{sec:method}

The original capture archive is kept for experimental checks but is not an available source during recovery.

\subsection{Captured history and physical file identities}

A logical node records an operation and its input node identifiers and parameters, together with its output hash and byte size and replay support. The environment record includes the numerical package versions and implementation hashes used by supported operators. Arrays use the recorded binary serialization and supported model classes use the project model codec, so the recovery claim concerns those captured bytes rather than a model with merely similar accuracy.

Several logical nodes can refer to the same physical payload, and the planner must not charge that payload once for each occurrence. Let $B$ be the captured physical blobs and let $w_b$ be the nonnegative size of blob $b$. The mapping $\beta(p)$ identifies the physical output of producer $p$, and $D(p)$ is the set of physical inputs it requires. Multiple recorded producers can therefore supply one blob, while an operation requiring several inputs needs all of them. Nonreplayable nodes keep their provenance but do not create executable recovery paths.

Mandatory roots $R\subseteq B$ must be retained and the protected targets are $T\subseteq B$. Targets can include models and probability arrays or earlier features needed for investigation. All methods in a comparison use the same captured manifest and root obligations. A method cannot read an omitted file from the capture archive, infer missing bytes from their hash or silently replace a target with a newer model.

\subsection{Recovery contract and byte objective}

The capability map assigns a replayable producer to a declared group, and several producers can share a group when they rely on the same unavailable entry point. Ungrouped producers remain available. For group set $G$ and bound $k$, the allowed losses are
\begin{equation}
  \mathcal{F}_k=\{F\subseteq G: |F|\leq k\}.
  \label{eq:faults}
\end{equation}
The contract covers processing loss while retained files and mandatory roots remain intact. A changed environment or a corrupt retained file can cause a refusal rather than a recovery guarantee.

For retained set $S$, grounded recovery begins with $A_0=S$ and repeatedly adds outputs of surviving producers whose inputs are already available:
\begin{equation}
 A_{i+1}=A_i\cup\{\beta(p):p\text{ survives }F,\ D(p)\subseteq A_i\}.
 \label{eq:closure}
\end{equation}
The process stops at the least fixed point $\operatorname{cl}(S,F)$. Beginning from retained values prevents an unsupported cycle from counting as a recovery path. The complete preservation problem is
\begin{align}
  \min_{S\subseteq B}\quad & m+\sum_{b\in S}w_b \label{eq:objective}\\
  \text{subject to}\quad & R\subseteq S,\nonumber\\
  &T\subseteq\operatorname{cl}(S,F)\quad\forall F\in\mathcal{F}_k,\nonumber
\end{align}
where $m$ is the fixed manifest and serialized contract size. Roots and metadata are included in reported retained bytes and paid once. A separately imposed byte budget can make the complete contract infeasible, and maximizing partial recovery below that minimum is a different objective.

\subsection{General exact formulations}

The scenario formulation shares binary retain variables across the allowed losses and adds availability and producer choices for each scenario. If a producer is used, every input must be available and the producer's output must have a later rank than its inputs. These ranks rule out ungrounded cyclic explanations. The formulation minimizes the payload term in Equation~\ref{eq:objective} and checks the selected store using grounded recovery after solving. Enumerating $\mathcal{F}_k$ can become expensive as the group count and loss bound grow, and the reference implementation refuses grids above its declared scenario limit.

The second formulation uses a storage master with one retain variable $x_b$ per physical blob and a separation oracle. The oracle looks for an allowed loss $F$ and a closed set $C$ that contains the selected files but omits at least one target. Closure means that every surviving producer with all inputs in $C$ also has its output in $C$. Such a witness proves that the selected store cannot recover every target for that loss, and every valid store must then satisfy
\begin{equation}
  \sum_{b\in B\setminus C}x_b\geq 1.
  \label{eq:cut}
\end{equation}
The master adds this necessary constraint and chooses another minimum cost candidate. If the master optimum is proved and the oracle proves that no such witness exists, the store is robust and storage optimal within the recorded model. A timeout or an invalid incumbent is recorded as unknown rather than a certificate. This candidate and oracle design follows established implicit hitting set and abduction ideas~\cite{hittingset}.

The implementation checks binary values and the objective and roots and learned constraints before accepting an incumbent. The automatic dispatcher first attempts the DAG specialization below and otherwise chooses the scenario route when there are at most 64 allowed scenarios and the master and oracle route above that threshold. The threshold is an engineering choice rather than a guarantee of the fastest solver, and solver status and postchecks remain necessary for either general route.

\subsection{Guarded DAG specialization and its certificate}

The specialized route requires a physical dependency DAG after mandatory roots are treated as available, and each optional blob must have at most one replayable producer. The guard rejects physical cycles and multiple replayable producers for the same output. Physical identity matters here because two logical producers with identical output bytes still violate producer uniqueness.

For this subclass, universal recovery when $k\geq1$ is equivalent to recovery with all grouped producers disabled together:
\begin{equation}
 \bigcap_{F\in\mathcal{F}_k}\operatorname{cl}(S,F)
   =\operatorname{cl}(S,G).
 \label{eq:collapse}
\end{equation}
This is a reasoning equivalence for a fixed store and does not declare the simultaneous loss of all groups to be an allowed runtime failure. To see why it holds, consider the blobs in topological order. A retained blob is always available, an unretained blob whose sole producer can fail is not universally available, and a blob with an ungrouped sole producer is universally available exactly when all its inputs are. These are the same rules obtained by disabling all grouped producers. For $k=0$, no producer is disabled.

After that reduction, an unretained blob with no surviving producer is a failure source. Failure can propagate along a dependency edge if the consuming operation needs the unavailable input, while retaining a blob stops propagation at that point. Protecting the targets therefore becomes a weighted vertex cut between failure sources and targets. We split each optional blob into input and output vertices joined by a capacity-$w_b$ edge, and dependency edges and terminal connections receive capacity
\begin{equation}
  M=1+\sum_{b\in B\setminus R}w_b.
\end{equation}
An optimum cannot cut an $M$ edge because retaining all optional blobs costs less. This is the standard vertex-splitting construction applied to the stated preservation model~\cite{flow}, and roots and fixed metadata are added to the selected payload cost.

The implementation obtains an integer maximum flow and a corresponding cut using NetworkX. Its checker validates every flow edge and capacity and conservation constraint, then removes the selected retained vertices and checks that no failure source reaches a protected target. The optional retained weight must equal the feasible flow value. Feasibility of the retained cut gives an upper bound and feasibility of the flow gives a lower bound, so equality certifies the optimum without rerunning the optimizer. A separate grounded-closure check verifies that the selected store actually protects the targets.

The equivalence does not extend to arbitrary AND/OR histories. If two producers in different groups can create one target from a retained root, either producer may survive any single group loss even though disabling both destroys recovery. An ungrounded physical cycle also breaks the failure source argument. These cases explain why the eligibility guard and general fallback are part of the method.

\subsection{Components and recovery execution}

An optional decomposition removes mandatory roots from the live dependency connectivity graph and solves components with targets separately. Their selected payloads are combined while the original global metadata and roots are paid once, and internal solver projections are not written as capture manifests. Shared failure labels do not invalidate this decomposition under the universal contract because each component must satisfy every allowed loss of its own relevant groups. A single optional target with only producers that depend only on roots also has a direct rule: it need not be retained if an ungrouped producer exists or the number of distinct producer groups exceeds $k$.

The executor builds a grounded witness from the actual retained store and surviving producer view and follows it in dependency order. Each request has its own memo and trace, and recovered or loaded payloads must match their recorded hashes. Missing files and source mismatches and corrupt retained bytes are reported explicitly. Stores are trusted local artifacts and the general restorer checks its supported runtime contract before loading values, and the execution never treats an unavailable producer as a usable alternative.

When all requested targets are already retained, the standard-library export route verifies their sizes and SHA-256 identities and materializes the output files without deserializing model objects. If a target is absent it returns control to ordinary replay, and if a retained target is corrupt it fails rather than bypassing the error. Exact file export is distinct from executing an old model in an incompatible environment. These are immutable-artifact recovery rules and do not establish distributed crash consistency or exactly-once external side effects.

\subsection{Histories and declared processing changes}

The new shared loss grid uses Wine and Breast Cancer from scikit-learn~\cite{datasets}. We split observations into 75\% training and 25\% test data using stratification and the three fixed seeds 20261016, 20261017 and 20261018. Features are divided into two disjoint column views and each view is standardized using only training observations. Logistic regression versions span a fixed regularization range from $10^{-3}$ to $10^3$, and every configured version is kept. In the fused boundary the downstream stages consume both views directly, while the other boundary records their concatenated matrix as an additional artifact.

Each captured history is tested with separate preprocessing groups and then with one shared group covering both standardization entry points, with $k=1$. The same captured physical bytes are used across the paired contracts. The shared contract is an exploratory follow-up motivated by a disclosed favorable pilot, and both small histories and explicit-concat controls remain in the full grid. No production outage frequency is estimated.

The scientific matrix has four recipe adaptations: Iris feature union, Digits PCA, Diabetes polynomial features and Digits forests. Two seeds and three versions give eight captures, and the matrix varies preprocessing versus broad loss with $k\in\{0,1,2\}$. Its five budgets are based on fixed root and metadata costs plus 0, 10, 25, 50 or 100\% of optional payload bytes of target snapshots, so the budget construction does not depend on an optimum found later. Across eight methods this gives 1,920 method and budget rows.

The retinal study uses all 20 STARE fundus images and Hoover vessel annotations~\cite{stare}. Images are resized to $64\times64$ RGB and split by image into 15 training and five test images, with 6,000 sampled training pixels. Three seeds, two model families and three history lengths give 18 captures. A legacy three-pixel feature shift is replaced by an aligned extractor and the two revisions must produce different feature bytes. Targets are either models and predictions or those files plus investigation features, and the contracts cover intact processing, loss of the legacy extractor or loss of training and prediction. Model settings also change across versions, so the experiment does not isolate the revision's causal effect on accuracy. The histories overlap but are not literal nested prefixes despite that wording in the original protocol.

The large study uses all 20,000 UCI Letter observations with 16 features and 26 classes~\cite{letter}. A stratified split with seed 20261015 gives 15,000 training and 5,000 test observations, and train-only MinMax scaling and chi-squared selection retain 12 features. The fixed 16 forests combine 64/128/192/256 trees with two feature-sampling settings and two model seeds. They are genuinely trained models and no padding or duplicate payload is introduced to reach a storage target.

\subsection{Comparators and budget fairness}

The exact comparators solve the same complete preservation obligation. The robust greedy policy adds the best grounded coverage gain per byte, and the stronger local policy also reverse-deletes from a full store and tries exchanges that add one artifact followed by pruning. These are our implementations and the local policy allows at most two exchange passes, so a gap against it is not a claim against every local-search algorithm. Target snapshots keep protected outputs directly. A manual frontier control chooses the smallest feasible workflow-specific frontier, which tests whether expert knowledge can match automatic selection.

The HYPPO rank and frequency methods use a pinned released component and HELIX uses a documented rule adapter. They share the executor and byte accounting with the retention methods but preserve their reuse-oriented selection criteria. In the new cloud grid these adapters receive the exact minimum total byte budget, whereas robust heuristics and snapshots receive the full candidate allowance when comparing complete store sizes. The scientific matrix instead gives all methods the same fixed budget at each point. Comparisons must therefore report their budget and objective rather than collapse every method into one universal ranking.

The native DVC study uses DVC 3.67.1 and gives it the certified optimal retained payloads without charging selection time. One downstream batch stage avoids a separate Python startup for every model, and correctly retained target cache objects can let DVC skip that stage. Before each trial both methods have the same paid physical payloads and no unpaid downstream cache objects, with distinct-inode byte checks and hard links used for common retained files. DVC configuration is recorded separately from the common payload objective. Both authored workers can use the exact file-export helper.

The later encoded storage study retains the previous flat optimum as a candidate, adds exact prefix and suffix deltas with their bases and headers charged, and measures a joint archive of retained canonical payloads. The final selector computes the flat exact, delta exact, flat local, delta local and separately compressed choices and keeps the smallest complete store. We compare it with the previous flat and delta implementation, a joint archive of the flat optimum, and local search with all offered formats. The first three-candidate version lost three conditions to the strengthened local control; adding both local plans was a disclosed correction after that result. Every row in the later table uses the final five-candidate selector, and the original losses remain saved in the artifact~\cite{artifact}. The exact reference only certifies the declared flat or delta inventories, not a global optimum over every jointly compressed retained set.

The later storage catalogue has 216 primary, 48 scientific transfer, 72 three-seed cloud and 108 retinal conditions, plus two Letter conditions whose complete paired storage values are unavailable. These conditions share captures and were chosen for this project, so win fractions describe the catalogue rather than an estimated production probability. All stored byte totals include metadata, mandatory roots and delta bases. Saved file and export checks confirm exact identity but are not new full-grid model replay requests. The joint archive is decoded into memory and uses a temporary retained store for replay; its compression time and peak memory were not benchmarked.

The broader native DVC census has 72 captures from six datasets, four recipes and three history lengths. Three loss contracts, two request sizes and command line or warm API access make 864 configurations, each timed in three paired randomized-order repetitions. The methods receive the same certified optimal retained payloads. The elapsed call includes requested-file inventory and hash verification but excludes capture, planning and setup, and OS caches are not flushed. A separately coded direct executor supplies a control for the cost of DVC orchestration~\cite{artifact}.

\subsection{Machines, repetitions and recorded outcomes}

The shared loss study runs one fixed seed block on each of three Linux GitHub runners exposing four virtual CPUs on AMD EPYC 7763 hosts. The native study uses runners exposing four CPUs with EPYC 9V74 for one block and EPYC 7763 for two. Python is 3.12.15 with NumPy 2.3.5 and SciPy 1.17.0 and scikit-learn 1.8.0, and numerical execution is limited to one BLAS thread. These are separate runner blocks of the same constructed workload design rather than multi node scale-out.

Each cloud planner has three timed calls per case and the earlier 48-condition replanning study has five. General solver calls use a 30 s limit and a requested relative MIP gap of zero, with 120 s allowed in Letter. The polynomial flow route does not enforce a hard interruption deadline. A native recovery comparison has three paired trials with deterministically randomized method order. Its primary elapsed time includes cold subprocess and CLI startup and final common SHA-256 verification, while setup and planning are excluded and worker timings and CPU are logged separately. OS page caches are not flushed. The final native revision follows earlier exploratory corrections and is not pooled with them.

Every actual request records whether its expected target identities were recovered, whether a deficient store was correctly blocked and whether an unexpected outcome occurred. When methods select identical stores they share explicitly attributed execution evidence, so method totals must not be summed as new physical requests. Ratios are computed within a history from method medians and then summarized across histories. These descriptive ratios and repeated requests do not establish population significance.

The older concurrency control uses a Linux Xeon Platinum 8573C host with a CPU quota of eight cores and Python 3.12.14. It randomizes 54 trials across three policies and two data sizes and three worker counts and three repeats. All five versions are warmed before a timed trial and each request has a fresh restorer and memo. Service latency includes environment validation and disk recovery, while response latency also includes queue wait. Throughput excludes capture and planning, and its resource sampler records CPU and RSS for the whole benchmark process. This is not a concurrency evaluation of the newer native DVC integration.

\section{Discussion and Reproducibility}
\label{sec:discussion}

The contract prioritizes complete recovery and minimum retained bytes, while recovery latency remains a separate cost. Manual frontier ties and faster snapshot loads show why no policy wins every objective.

The histories use public data but their processing graphs and losses are constructed, and the shared-loss pilot and earlier native revisions informed later experiments. The encoded-storage catalogue also reuses captures and its final candidate choice was corrected after a stronger local control revealed three losses. Seeds, versions, contracts and requests share data, so the paired summaries are descriptive rather than population estimates. The retinal adaptation is not the private EyeAI workflow and Letter's byte gain depends on representation. Annotation effort, deployment cost and the prevalence of retired capabilities remain unmeasured.

The artifact preserves source hashes and captured identities and raw timestamps and solver states with the analysis scripts~\cite{artifact}. Fresh capture and replay on three runners do not establish portable replay across arbitrary software changes. Six original nonforest scientific captures lack a closed global end of run source guard after an interruption, although their snapshots and request guards and raw reconciliation remain. One original Letter archive container is missing; four recovered frontier payloads match their original hashes in a separately identified replacement archive. Available-file integrity and original-container completeness are separate checks.

The supplied script regenerates the original figures from pinned recorded inputs, while the later storage and recovery ledgers are linked in the repository artifact~\cite{artifact}. New benchmark executions require a fresh output directory. No GPU was used in these studies. The joint archive decodes retained content into memory, and its latency, compression cost and peak-memory tradeoff remain unmeasured. Larger neural training states, distributed scale out and crash consistency require separate implementation and evaluation.

\section{Conclusion}

RecoverML selects files under an explicit historical preservation contract and checks their recovery and byte identities. General exact formulations and a guarded DAG specialization support different recorded graph shapes. Shared preprocessing loss exposes storage choices missed by the tested local heuristic, while a stored shared intermediate removes that gap and manual frontiers still match the optimum. The later flat, delta and joint archive choice reduces storage against the previous flat optimum in 244 of 444 measurable conditions and against equal-format local search in 20, with 424 local ties and no measured losses after the disclosed correction. The broader native DVC census finds a consistent elapsed-time advantage at equal retained payloads, while a direct executor is near parity. These results establish selective storage and orchestration benefits within the tested contracts, and independently collected workflows remain needed to judge how often those benefits arise in practice.
